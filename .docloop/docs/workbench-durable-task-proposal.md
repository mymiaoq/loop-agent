# 工作台持久任务、补充资料与产物版本管理方案

日期：2026-11-03。状态：供用户决策的方案草案，未审批、未实施，不替代任何已审批基线。

## 1. 结论与需求理解

建议沿用 Python + LangGraph + SQLite，在现有工作台上实现持久任务控制；无需为当前单机、单任务执行引入新的工作流平台。界面调整较小；暂停恢复为中等改造；运行中补充资料后的影响分析与部分重做最复杂。不能用几个前端按钮替代后端持久执行。

需求包括：右侧始终保留当前任务工作区；资料、记录、Skills、设置使用弹层；Skills 显示易懂名称和功能，不显示内部 ID；运行支持暂停、取消、故障恢复；刷新只重连原任务；补充资料时保存进度、比较需求与当前实现、重新规划；正式产物提交并上传 Git，并可查看版本与产物的对应关系。

本方案的默认建议均待决定，不视为用户已经批准。此次仅交付分析文档，没有修改产品代码、审批、运行数据，也没有提交或推送仓库。

## 3. 成熟方案选型

| 路线 | 优点 | 成本和局限 | 建议 |
| --- | --- | --- | --- |
| LangGraph 持久检查点 + 业务控制表 | 延续现有依赖，支持节点状态保存与人工中断 | 需自行实现调度、取消、结果落盘一致性和副作用去重 | 当前推荐 |
| Temporal + LangGraph | 持久工作流、事件历史，适合长期多 Worker 任务 | 增加服务部署、运维和执行模型适配 | 后续多机规模再评估 |
| 仅前端存状态或暂停后台线程 | 改动看似较少 | 不能跨进程/断电恢复，也不能可靠防止重复写入 | 不采用 |

LangGraph 官方提供持久检查点、固定 thread_id 和 interrupt/Command 恢复机制；恢复可能重入中断节点，因此中断前的副作用必须可去重。Temporal 提供持久工作流及事件历史。两者都不能替应用自动判断需求变更、产物是否有效或任意外部写入是否已经成功。

参考：[LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence)、[Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)、[Temporal Workflow Execution](https://docs.temporal.io/workflow-execution)、[Git Tagging](https://git-scm.com/book/en/v2/Git-Basics-Tagging.html)。实施以 uv.lock 内实际版本验证，不直接照搬最新文档里的新 API。

## 4. 界面与交互

桌面保留左侧任务列表和右侧任务工作区。辅助弹层覆盖在当前页面上，关闭后保留任务、筛选、滚动和编辑状态；后台任务不依赖弹层存活。窄屏弹层可占满视口，右侧工作区仍是主页面内容，不强行挤成两列。

资料弹层提供上传、版本和任务关联；记录弹层提供历史运行和事件检索，右侧仍保留当前任务实时进度；Skills 弹层使用“需求规格整理｜把资料转成带验收标准的需求”等名称加功能形式，并可展开说明；设置弹层按当前项目展示仓库和模型。内部引用、路径和 Hash 继续写入审计数据，但不展示在 Skills 用户界面。

弹层支持焦点约束、Esc、关闭后焦点返回入口、长列表滚动及未保存编辑提醒。右侧运行控制按状态显示暂停、继续、取消或恢复，不允许重复点击产生重复 Worker。

## 5. 持久任务与恢复

### 5.1 状态与身份

区分长期 task_id、不可变需求 change_id/spec_hash、每次执行 run_id、输入资料 input_revision 和执行尝试 attempt。普通暂停恢复沿用 run_id 和 thread_id；需求变化创建关联新 Change/Run，旧运行保留，不覆盖原审批。

建议运行状态：queued、running、pause_requested、paused、cancel_requested、cancelled、interrupted、waiting_confirmation、succeeded、failed、blocked、superseded。需求审批状态与运行状态分别存储；interrupted 表示执行进程失联，blocked 表示依赖或门禁阻塞，不能混用。

持久化节点位置、已完成 TASK、输入资料版本及 Hash、Spec Hash、产物 Hash、尝试记录、剩余额度、worker 租约、执行器/图版本、代码基线和本地 Skill 来源快照。延续运行恢复既有输入；有意采用新 Skill 或规则时显式建立新尝试/变更，不能静默漂移。

### 5.2 操作语义

| 操作 | 行为 |
| --- | --- |
| 页面刷新/关页 | 只停止前端观察；再次打开查询同一运行，不调用 start |
| 暂停 | 立即持久化指令，在安全步骤停止，落盘后才显示已暂停 |
| 模型分析中暂停 | 支持时取消请求；已完整落盘的分段结果保留，未完成调用标记中断，继续时可能重试 |
| 继续 | 校验基线、检查点、执行器版本及权限，从未完成步骤继续 |
| 取消 | 终止当前运行，保留日志和产物；不自动回滚已发生的外部操作，不作为普通暂停继续 |
| 服务停止/断电 | 重启后识别失效租约，进入 interrupted；核对状态后展示可恢复位置 |
| 恢复 | 默认由用户点击恢复；自动恢复可作为后续配置，存在不确定副作用时必须先核对 |

“断电恢复”的承诺边界是恢复最后一次可靠落盘的进度，不是保存 Python 线程堆栈或模型尚未返回的推理。磁盘损坏需要备份恢复；Git 管正式产物，不能替代运行数据库、资料对象与检查点的一致性备份。

### 5.3 一致性与防重复

启动/继续/取消 API 使用请求幂等键及状态版本锁；控制指令落数据库，Event 仅用于唤醒。后台执行持有租约和执行代次，旧 Worker 失去写入资格；单机继续保留现有独占锁与并发上限 1。

每个有副作用步骤记录 pending/started/completed/unknown，稳定键绑定 run、节点、输入版本及操作。文件采用临时文件、原子替换、Hash 校验；写 Git、上传等操作恢复前核对真实结果。无法判断是否完成时进入待核对，不盲目重试。不能声称所有外部服务都能实现严格 exactly-once。

SQLite 检查点、业务数据库和文件不假定处于同一事务：产物先可靠落盘，再登记完成状态；重启通过清单与 Hash 对账。检查点缺失或版本不兼容时阻塞并说明原因，不能悄悄从头运行。

## 6. 运行中补充文档

建议流程：接收上传并固定版本 → 持久化暂停请求 → 当前安全步骤结束并保存进度 → 分析新增资料 → 生成差异与影响报告 → 用户确认新方案/审批 → 按新计划继续。

上传到当前任务和仅存入项目资料库分开：前者触发暂停，后者不影响无关任务。上传先存入待分析批次；在暂停完成前不改变原运行的输入。连续上传合并或排队，以 input_revision 标记；旧批次分析迟到返回时不得覆盖新批次。

“现有功能”需分开比较：原批准需求、当前计划及已完成记录、业务仓库实际实现与验证证据。报告逐项列新增、修改、删除、冲突、不影响，并列引用位置、受影响 REQ/AC/TASK/TC、可复用产物、失效产物、重做步骤和待确认项。没有实现或证据时标为未实现/未知，不能拿规划当已实现。

无语义变化时可保持原基线继续；有需求变化时创建关联新 Change，展示新旧差异并重新审批，原基线原字节不动。默认不在分析后自动执行未批准的需求。只重做被影响步骤及依赖它们的验证/审查；产物复用必须具备输入、依赖和 Hash 依据，第一版可以保守重做受影响阶段。

当前导入范围是 UTF-8 Markdown/TXT、单文件不超过 2 MiB。建议第一版沿用；PDF、DOCX、扫描件/OCR 是额外解析范围，应另列验收，不能因为界面写了“上传文档”就默认支持。

## 7. Git 产物版本管理（最高优先级）

### 7.1 管理边界与首次整理

区分框架自身版本和每个业务项目交付版本。框架源码留在当前仓库；业务代码及允许上传的正式产物默认进入该项目登记的仓库，不把所有项目材料集中推到框架 origin。

首次建立版本前，盘点已有产物及所在目录、检查已有 commit、验证远端目标与推送权限。仅白名单复制正式文档、审批、证据、可交付代码及归档清单；数据库、检查点、模型输入、凭据、原始上传资料和临时文件保留在 agent-loop-data，不整体加入 Git。仅对已允许公开或入库的交付材料生成快照；上传资料若要入库须另行明确范围。

历史材料按实际证据登记：能证明对应代码提交则记录；无法证明则写“历史导入，对应代码版本未知”，绝不把今天 HEAD 倒填成历史版本。

### 7.2 发布结构与清单

建议使用 `deliverables/<delivery-version>/` 存不可变产物快照，根文档 `文档/产物版本索引.md` 用于人工查看，目录内 `manifest.json` 用于程序校验。版本号需区分框架版本与交付版本；建议交付版本使用日期加序号并附不可变 tag，避免和项目语义版本混淆。

清单至少包含：交付版本、项目、任务、Change、Spec Hash、Run、输入版本、来源代码 commit、真实验证状态、产物相对路径/大小/SHA-256、时间及上个版本。索引显示版本、变更摘要、来源代码版本、产物目录、验证状态及查看链接。未验收快照明确标识，不能冒充正式已验收发布。

发布 commit 的自身 Hash 无法预先写入同一 commit 的文件。采用：清单记录来源代码 commit；不可变 tag 指向包含产物和索引的发布 commit，二者通过 Git 解析关联。若需要书面记录完整发布 Hash，写入后续独立发布记录，不能循环改写同一提交。

### 7.3 发布与上传过程

冻结产物 → 生成清单和索引 → Hash 校验 → 按白名单提交 → 创建版本 tag → 推送指定分支/tag → 查询远端对应引用确认。

Git 状态独立于执行状态，至少区分：待归档、已本地归档、已本地提交、待上传、上传失败、远端已确认。断网不丢版本、不重新执行任务；重试上传复用已有 commit/tag。部分推送成功时分别记录分支和 tag，不强推、不静默覆盖远端已有版本。

工作台“查看产物”增加“当前运行/历史发布版本”切换，点击版本可见清单、来源代码和正式文件。上传状态保存在本地发布账本并核验远端；不能让发布 commit 内的文档预先宣称自己已经上传成功。现有动态交付总览继续作为工作视图，正式发布读取冻结快照。

## 8. 分阶段交付与验收

| 阶段 | 交付内容 | 核心验收 |
| --- | --- | --- |
| P0 | 现有产物盘点、清单、索引、Git 提交和上传状态；辅助弹层和 Skills 展示 | 从版本定位产物/代码；断网重试不新建版本；弹层关闭保持工作区；不展示 Skill ID |
| P1 | 分析与规划统一持久运行，暂停/取消/继续、刷新重连、故障恢复 | 刷新不新增 Run；暂停无后续副作用；重启从持久节点续跑；未知外部写入阻塞核对 |
| P2 | 任务补充文档、差异报告、新审批和受影响步骤重做 | 上传停旧输入；报告引用明确；新基线批准前不执行；旧产物可追溯；连续上传不串批次 |

P0 的文档/发布数据结构先确定，后续恢复与重规划共享它；P1 先于 P2。界面与后端可以在契约确定后隔离开发，共享存储和运行控制文件按依赖顺序整合。暂不新增业务编码执行器、多机队列或 Oracle 原生检查点，这些不属于生命周期改造的隐含交付。

测试使用系统临时目录、临时 Git 仓库与本地 bare 远端、受控模型 fixture；不复用用户资料和设置。覆盖进程强制终止、落盘前后崩溃、重复请求、旧 Worker 迟到、审批/输入变更、Git 提交后未登记、推送后未登记及恢复版本不兼容。

浏览器验收覆盖 1920/1366/窄屏、键盘与焦点、长文本、关闭弹层、刷新与任务切换。实现阶段运行 `uv run python -m unittest discover -s tests -v` 和 `uv run docloop doctor`，并分开记录真实模型、真实 Git 远端和真实断电的验收；模拟杀进程不写成已完成物理断电验收。本次仅文档分析，未运行上述实现验收。

## 9. 决策建议

建议批准“沿用 LangGraph，按 P0→P1→P2 实施”的方向；先把现在已有产物纳入可追溯版本管理，再扩展运行生命周期。默认安全节点暂停、故障后手动恢复、补充资料变更需求后重新审批、第一版支持现有 Markdown/TXT。

实施前最关键的业务选择是：产物跟随各项目代码仓库，还是使用单独的交付仓库；本方案推荐跟随各项目代码仓库。远端位置、允许上传的现有材料范围需在实际首次发布时落实，不能凭框架 origin 推断。
